# Лабораторная №3. Базы данных и отношения между таблицами

**Предметная область:** система проведения экзаменов. Spring Boot 3.3.5, Java 17+, Spring Data JPA, PostgreSQL. REST API + HTTP Basic для учебного административного доступа. Основание: `zadanie3.pdf` (содержательные требования, без посторонних вставок).

## Предметная модель

| Таблица | Основные атрибуты | Связи |
|---|---|---|
| `users` | id, name, email (unique) | 1:N `exam_attempts` |
| `exams` | id, title, passing_score, time_limit, status | 1:N `exam_tasks`, 1:N `exam_attempts` |
| `exam_tasks` | id, exam_id, description, reference_answer, max_score | N:1 `exams`, 1:N `task_solutions` |
| `exam_attempts` | id, exam_id, user_id, start_time, end_time, final_score, status | N:1 `exams`, N:1 `users`, 1:N `task_solutions` |
| `task_solutions` | id, attempt_id, task_id, student_answer, score | N:1 `exam_attempts`, N:1 `exam_tasks` |

**Ограничения на уровне БД:** PK/FK, уникальный email; неотрицательные баллы; положительное время; допустимые статусы; уникальность `(attempt_id,task_id)`; не более одной попытки `IN_PROGRESS` на пользователя (частичный уникальный индекс PostgreSQL); проверки непустых полей. Ограничения логики, требующие связанного состояния, реализованы транзакционными сервисами, не только CHECK.

## Подготовка PostgreSQL (Arch Linux)

1. Установите PostgreSQL (`sudo pacman -S postgresql`), инициализируйте кластер **только если он ещё не инициализирован**, включите сервис. Например для нового кластера: `sudo -iu postgres initdb -D /var/lib/postgres/data --locale=C.UTF-8 --encoding=UTF8` и `sudo systemctl enable --now postgresql`. Если кластер уже существует, **не запускайте initdb повторно**.
2. Из корня проекта выполните от системного пользователя postgres:

   ```bash
   sudo -iu postgres psql -d postgres -v ON_ERROR_STOP=1 -f "$(pwd)/db/00_create_database.sql"
   sudo -iu postgres psql -d exam_db -v ON_ERROR_STOP=1 -f "$(pwd)/db/01_schema.sql"
   sudo -iu postgres psql -d exam_db -v ON_ERROR_STOP=1 -f "$(pwd)/db/02_seed.sql"
   ```

   **Примечание:** `sudo -iu postgres` может не иметь доступа к вашему домашнему каталогу (`/home/...`). В этом случае перенесите SQL в доступный временный каталог с правами чтения либо запустите `sudo -iu postgres psql ... < db/00_create_database.sql` (аналогично для других файлов); для запусков без доступа к каталогу используйте перенаправление stdin: `sudo -iu postgres psql -d postgres -v ON_ERROR_STOP=1 < db/00_create_database.sql` (аналогично остальным скриптам). Пароль задаётся отдельной командой после создания роли.
3. `00_create_database.sql` создаёт `exam_db` и роль `exam_app` (если отсутствуют). Затем задайте пароль интерактивно: `sudo -iu postgres psql -d postgres -c "\password exam_app"`. **Не записывайте пароль в скрипт или Git.** `01_schema.sql` создаёт таблицы и даёт роли только `SELECT/INSERT/UPDATE/DELETE`, `USAGE` на схему/последовательности. Роль не может создавать/удалять таблицы. `02_seed.sql` добавляет двух пользователей, два экзамена, задания и завершённую попытку. ID демонстрационных записей начинаются с 90001. Скрипты предназначены для локальной учебной БД, на которой схема ещё не была создана; для базы с уже существующими объектами сделайте резервную копию и сверьте ограничения.
4. Подключение от `exam_app` через TCP, а не peer-сокет: `psql -h 127.0.0.1 -U exam_app -d exam_db -c 'select count(*) from exams;'`.

## Переменные окружения и запуск

```bash
export DB_URL='jdbc:postgresql://localhost:5432/exam_db'
export DB_USERNAME='exam_app'
export DB_PASSWORD='ПАРОЛЬ_РОЛИ_ИЗ_ШАГА_2'
export APP_ADMIN_USERNAME='admin'
export APP_ADMIN_PASSWORD='СВОЙ_НАДЁЖНЫЙ_ПАРОЛЬ'
./mvnw clean test
./mvnw spring-boot:run
```

`application.yml` использует значения из env. `DDL_AUTO=validate` по умолчанию: Spring проверяет уже созданную схему и **не создаёт** её от имени ограниченного пользователя. Для локальных проверок можно переопределить `DDL_AUTO`, но для сдачи рекомендуется `validate`. Никакие реальные пароли не включены в проект. В HTTP Basic пароль передаётся в заголовке, поэтому для доступа за пределами localhost нужен HTTPS. Это административный сервис, отдельная студенческая авторизация не реализована.

## Пять бизнес-операций (отдельно от CRUD)

1. **Начало попытки** `POST /api/exam-attempts/start?examId=...&userId=...`: требует ACTIVE-экзамен и существующего пользователя, проверяет другие незавершённые попытки, фиксирует время начала (Exam + User + ExamAttempt).
2. **Отправка и проверка ответа** `POST /api/task-solutions/submit?attemptId=...&taskId=...`, JSON `{"answer":"SELECT"}`: проверяет статус/время попытки и принадлежность задания экзамену, один ответ на одно задание; начисляет 0 или максимальный балл (ExamAttempt + ExamTask + TaskSolution).
3. **Завершение попытки** `POST /api/exam-attempts/{id}/finish`: суммирует решения, сравнивает с порогом экзамена, учитывает срок и фиксирует PASSED/FAILED (ExamAttempt + TaskSolution + Exam).
4. **Публикация экзамена** `POST /api/exams/{id}/publish`: запрещает публикацию без заданий или при проходном балле выше суммы максимальных баллов (Exam + ExamTask).
5. **Отчёт студента** `GET /api/exam-attempts/report/{userId}`: агрегирует данные пользователя и его попыток (User + ExamAttempt); возвращает общее число попыток, успешные, максимум баллов и долю успеха. Отчёт не изменяет данные; требование PDF для поиска выполняется за счёт обращения к двум связанным сущностям.

**Недопустимые состояния:** старт DRAFT; одновременные активные попытки; повторная отправка решения; ответ на задание чужого экзамена; ответы после срока или завершения; изменение опубликованных заданий/экзамена; повторный финиш. Транзакции и ограничения БД дополняют проверки сервиса.

## CRUD и коллекция запросов

Маршруты: `GET/POST/PATCH/DELETE /api/users`, `/api/exams`, `/api/exam-tasks` (для создания задания нужен `?examId=...`). Для `exam-attempts` создание = `POST /start`, чтение = GET, изменение состояния = `POST /{id}/finish`, удаление = DELETE; для `task-solutions` создание = `POST /submit`, чтение = GET, удаление = DELETE. **PATCH/PUT для ответов не предусмотрен намеренно**: повторное редактирование уже проверенного ответа меняло бы баллы. В БД все операции выполняются через JPA-репозитории, а не в памяти.

Полная Postman-коллекция: `postman/lab3.postman_collection.json`. Импортируйте её, укажите переменные `adminUser`, `adminPassword` и запустите папки по порядку. Тесты Postman сохраняют реальные идентификаторы, проверяют HTTP-коды, баллы, итоговый статус и запреты. Папка CRUD создаёт временные объекты и удаляет в правильном порядке, основная папка демонстрирует пять бизнес-операций, третья показывает удаление решений и незавершённых попыток. Дополнительные инструкции: `postman/README.md`.

## Запуск тестов

`./mvnw clean test` запускает исходные unit-тесты JUnit/Mockito и новые JPA-тесты на H2 (`DatabaseModelTest`); H2 используется только для тестирования ORM, приложение работает с PostgreSQL. Полный end-to-end сценарий проверяется Postman с работающим PostgreSQL. Для новой БД рекомендуется запускать SQL и Postman на отдельной учебной копии, не на продакшн-данных.

## Структура

- `src/main/java/` — контроллеры, сервисы, репозитории, сущности, конфигурация безопасности, DTO.
- `src/test/java/` — модульные тесты и тесты JPA.
- `db/00_create_database.sql` — роль с ограниченными полномочиями и база.
- `db/01_schema.sql` — схема, связи, индексы, CHECK/FK/UNIQUE и GRANT.
- `db/02_seed.sql` — тестовые данные.
- `db/03_verify.sql` — проверка таблиц, связей и прав роли приложения.
- `db/03_verify.sql` — проверка таблиц, связей и прав роли приложения.
- `postman/` — коллекция всех доступных CRUD-операций и демонстрационный сценарий.

**Известное ограничение:** при использовании базы, созданной ранее Hibernate (`ddl-auto=update`), некоторые ограничения из `01_schema.sql` могут не добавиться автоматически, поскольку `CREATE TABLE IF NOT EXISTS` не изменяет существующие таблицы. Используйте отдельную учебную БД либо миграции с предварительной проверкой. Для полноценной системы нужны роли студентов, миграции схемы и интеграционные тесты на PostgreSQL.
